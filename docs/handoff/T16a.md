# T16a: bot Action, memory, candidate modules

## What was done
Created the bot decision building blocks (the "brain" pieces of T16, excluding
worker.py/brain.py which are a later subtask). Bots only ever change the game
through `realm.services` functions; nothing here writes villages/troops tables
directly.

## Files
- `realm/bot/action.py` (new)
- `realm/bot/memory.py` (new)
- `realm/bot/modules.py` (new)
- `tests/bot/test_memory.py` (new, 10 tests)
- `tests/bot/test_modules.py` (new, 20 tests)

## Public functions
- `action.py`: `Action(kind, score, params, module)` dataclass;
  `Action.execute(s, bot, village, now, cfg)` dispatches to
  `villages.build` / `training.train` / `military.send_troops(Mission.RAID)`
  only; does not catch `GameError`.
- `memory.py`:
  - `new_memory() -> dict` — `{'last_report_id': 0, 'targets': {}, 'grudges': {}, 'grudge_updated_at': None}`
  - `update_from_reports(s, bot, profile, now, cfg) -> None` — decays grudges by
    `0.9 ** game_days` since `grudge_updated_at` (sets the timestamp when absent),
    reads the bot's `kind='battle'` reports with `id > last_report_id` ordered by id,
    updates `targets` on attack (win: last_raid_at/last_loot/last_losses, fails reset;
    loss: fails+1, fail_times appended) or grows `grudges[attacker_player_id]` when the
    bot was attacked (attacker player id resolved via the attacker village row).
    Assigns a NEW dict to `profile.memory` so JSONB change tracking sees it.
  - `recent_fails(memory, village_id, now, hours=24) -> int`
- `modules.py`:
  - `BotContext` dataclass (s, bot, profile, village, now, cfg, rng, memory, world,
    personality, levels, rows, troops_home) and `make_context(...)` which loads
    rows/levels/troops_home from the DB.
  - Module functions, each `(ctx) -> list[Action]` (only score > 0, tagged with
    `module=`): `field_upgrades`, `storage`, `build_order`, `training`, `raid`.
  - Shared helper `_first_empty_center_slot(rows)` (slots 20..38).

## Key implementation notes
- `field_upgrades`: gain per hour at level+1 minus level (× speed × production_mult),
  `base = 100 * gain / cost.total()`, `need = clamp(avg_gross/gross_of_resource, 0.5, 2.0)`
  (2.0 when that resource gross is 0); farm slots get `need = 3.0` when the net food
  rate from `villages.compute_rates` is below 10% of gross total.
- `storage`: uses `villages.compute_rates` for (rates, capacity); 85% thresholds;
  reuses the existing building's slot, else first empty center slot; skips at max
  level or with no free slot; at most one action per building type.
- `build_order`: first build_order entry with current < level, next level within
  max, and no missing requirements; slot = fixed_slot / existing center slot / first
  empty center slot.
- `training`: target = gross.total() × army_hours; army value over all troops with
  `home_village_id == village` (any location); unit picked with `ctx.rng.choices` over
  trainable `unit_mix` (fallback 'spearman'); count = `int(0.5 * min(stock/cost))`.
- `raid`: needs raid_radius > 0 and >= 5 home carry units; skips own villages,
  protected targets, and targets with `recent_fails >= 2`; expected loot =
  memory `last_loot` (>0) else 0.5 × carry; best `expected/distance × (1+grudge)`;
  action score `3 * min(1, expected/carry)`; sends all home carry>0 units.

## Limits / TODO
- `worker.py`, `brain.py` (think loop, personality weights, active_from_day
  0.3 multiplier, max_actions/skip_chance) are out of scope for T16a; the
  `module` field on `Action` is what brain.py will weight by personality.
- `Action.execute` raises `GameError` to the caller (brain must skip on error).
- `modules.raid` uses `village.protection_until` (set on Village rows) as the
  protection check per the task spec.
- Memory stores `last_raid_at` as ISO strings; `recent_fails` parses them with
  `datetime.fromisoformat` (all timestamps are timezone-aware UTC).
