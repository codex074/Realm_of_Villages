# T15a handoff — Phase 1 API endpoints + get_map

## What was done
Added the Phase 1 HTTP endpoints of BUILD.md section 9 (all under `/api`, sync `def` routes
using the same dependency style as `routes/villages.py`; every mutating route is guarded by
`require_running`):

- `GET /api/villages/{id}/train-options` → `list[TrainOption]` (`training.get_train_options`)
- `POST /api/villages/{id}/train` body `{unit, count}` → `TrainingView` (`training.train`)
- `POST /api/villages/{id}/send/preview` body `SendBody` → `SendPreview` (`military.preview_send`,
  NOT guarded by `require_running`)
- `POST /api/villages/{id}/send` body `SendBody` → `MovementView` (`military.send_troops`)
- `POST /api/troops/{troop_id}/recall` → `MovementView` (`military.recall_reinforcement`)
- `GET /api/map?cx=0&cy=0&r=7` → `MapView` (`worlds.get_map`); `r` outside 0..10 →
  `GameError(INVALID_TARGET, 'รัศมีแผนที่ไม่ถูกต้อง')` (HTTP 400)
- `GET /api/reports?before_id=` → `list[ReportSummary]` (limit 50, human player)
- `GET /api/reports/{id}` → `ReportDetail` (marks read)
- `GET /api/ranking` → `list[RankingRow]` (`ranking.get_ranking` for the current world)

Unknown mission strings (not a `Mission` value) raise `GameError(INVALID_TARGET,
'ภารกิจไม่ถูกต้อง')` in both send and preview.

## Files
- `realm/api/routes/military.py` (new): train-options, train, send/preview, send, recall.
  Helper `movement_view(s, m, cfg)` builds the outgoing `MovementView` (direction "out",
  `from_village = villages.village_brief`, `to = Coord(to_x, to_y)`, `to_village_name` from
  `to_village_id`, `units = m.units`, `hostile=False`); `parse_mission` for the mission check.
- `realm/api/routes/world.py` (new): `/map` (query params `cx: int = 0, cy: int = 0, r: int = 7`)
  and `/ranking`.
- `realm/api/routes/reports.py` (new): `/reports` (`before_id: int | None = None`) and
  `/reports/{id}`.
- `realm/api/schemas.py`: added `TrainBody(unit, count)` and
  `SendBody(to_x, to_y, mission, units, catapult_target=None)`.
- `realm/api/main.py`: included the three new routers with prefix `/api`.
- `realm/services/worlds.py`: APPENDED `get_map(s, world_id, player_id, cx, cy, r, cfg) -> MapView`
  (existing functions untouched). Center is torus-wrapped with `movement.wrap`; tiles are the
  (2r+1)² square ordered by y then x, each torus-wrapped. Exactly three queries: tiles, villages
  in the area (with their players), and one grouped buildings query for population
  (sum `pop_per_level * level`). Village dict: `id, name, player_id, player_name, tribe,
  population, is_mine, is_bot`.
- `tests/api/test_api_phase1.py` (new): 15 tests covering every acceptance criterion
  (train-options 9 entries / spearman missing [], train cost deduction + 400 INVALID_UNITS,
  preview distance 7.0 / 1800 s / carry 800 / DB unchanged, protected-target preview errors,
  send MovementView + arrive_at +1800 s, second send 400 NO_UNITS, unknown mission 400
  INVALID_TARGET, recall 200 / 403 FORBIDDEN / 404 NOT_FOUND, map 25 ordered tiles + center
  village is_mine/population 2 + edge wrap 48,49,50,-50,-49 + r=11 400 + bot tile is_bot,
  reports empty/newest-first/pagination/mark-read/unread count/403/404, ranking 3 rows 1..3,
  ended world: train/send/recall 409 WORLD_ENDED while preview/map/ranking/reports stay 200).

## Notes / limits
- `realm/api/routes/villages.py` needed no changes (train endpoints live in `military.py`).
- The map `get_map` raises on invalid radius before touching the DB; it does not guard on world
  status (read endpoint, per spec).
- The test world uses seed 1, speed 1, 2 bots; the first bot village is moved to (7, 0) and the
  second to (1, 0) to pin the map assertions.
- `test_send_too_many_troops` is implemented as a second send after the first consumed the
  troops (each test runs in its own rolled-back world, so a fresh world has 10 light_cavalry).
