# T11 handoff — Troop training + TRAIN_TICK

## What was done
- Implemented `realm/services/training.py` per BUILD.md 8.5 with the three public
  functions `train`, `tick_training`, `get_train_options`, following the lead's design
  notes exactly (lock -> owner check -> settle -> validate -> deduct -> queue ->
  schedule TRAIN_TICK -> after_change -> notify).
- Replaced the `TRAIN_TICK` stub in `realm/engine/handlers.py` with
  `handle_train_tick(s, ev, cfg)` which calls
  `training.tick_training(s, ev.payload["training_id"], ev.due_at, cfg)`.
  `HANDLERS` keys are unchanged; MOVEMENT_ARRIVE / ROUND_END still raise
  NotImplementedError, STARVATION_CHECK is still a no-op.
- Added `tests/services/test_training.py` with 10 tests covering: fresh-order stock
  deduction, queue row fields and the single pending TRAIN_TICK; ironwild 20% discount
  (floored costs); single tick; late worker (one call credits 3 units, a second call
  finishes and deletes the row, troop upserted not duplicated); second order chaining
  off the first `finishes_at`; food upkeep lowering `compute_rates` by 5 after 5
  spearmen; end-to-end through `engine.worker.process_next` (handler uses `ev.due_at`);
  all error codes (REQUIREMENTS_NOT_MET x2, INSUFFICIENT_RESOURCES with no side
  effects, INVALID_UNITS x3, FORBIDDEN, NOT_FOUND); and `get_train_options` output.

## Public functions
- `train(s, player_id, village_id, unit, count, now, cfg) -> TrainingQueue`
- `tick_training(s, training_id, now, cfg) -> None` (idempotent: missing row or
  `now < next_at` is a no-op; credits `min(remaining, 1 + (now-next_at)//per_unit_s)`)
- `get_train_options(s, player_id, village_id, now, cfg) -> list[TrainOption]`
- `handle_train_tick(s, ev, cfg) -> None` in `realm/engine/handlers.py`

## Design notes / limits
- `tick_training` does not mark the triggering Event row done; the worker does that
  (tests mark the event done manually to mirror the worker when calling the service
  directly).
- A training order is a single queue row per (village, building); a second order for
  the same building starts at the max `finishes_at` of existing rows for that building.
- `get_train_options` uses a large sentinel (`10**9`) for zero-cost resources when
  computing `max_affordable` (no unit in the current config has a zero-cost resource).
- Troop rows are upserted on (home, location, unit) via the UNIQUE constraint;
  `tick_training` settles the village before adding troops so upkeep applies from then.
- No `datetime.now()` anywhere in the new code; all times come from `now` / `ev.due_at`.
